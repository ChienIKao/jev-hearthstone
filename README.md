# Laya 爐石助手

本機 Laya 多語模型 + Power.log 局面讀取 + 規則篩選 + MuMu Android 觸控操作。

產品方向是爐石的日常作業助手。目前優先提供排位：選擇標準／開放與牌組、設定打法、連續對戰。每日任務、每週任務、活動任務列為後續迭代，尚未實作。

桌面介面分為「排位作業」「牌組與環境」「遊戲畫面」「進階設定」。排位頁顯示目前牌組、局數、執行狀態與紀錄；遊戲畫面獨立顯示，裝置位址、校準及單步控制集中於進階設定。

HSReplay 提供公開頁面文字匯入：保存環境牌組與留牌統計快照、資料來源、分段與日期，並將目前手牌相關的參考交給 Laya。另可保存每副牌組的 HTTPS 來源連結與環境筆記。筆記可記錄資料日期、分段、常見對手與應對策略，會隨換牌、一般選牌及出牌決策送給 Laya。來源連結本身不會自動下載攻略。依 [HSReplay 官方 API 文件](https://github.com/HearthSim/hsreplaynet-api-docs)，目前沒有全站彙總統計公開 API；因此本版不提供自動同步環境勝率或排名，目前透過複製公開頁面內容手動更新快照。牌組打法可由使用者填寫與審核；已為目前龍戰保存一份參考打法，並提供可關閉的留牌統計校正。

基本操作已有 MuMu 練習局驗證。Android 操作透過獨立於 Windows 游標的 ADB 觸控管道；Windows 原生輸入實驗另保留在原面板中。參考 [MAA MuMu 控制器](https://github.com/MaaAssistantArknights/MaaAssistantArknights/blob/dev-v2/src/MaaCore/Controller/MumuController.cpp) 與 [MaaFramework 控制方式](https://github.com/MaaXYZ/MaaFramework/blob/main/docs/en_us/2.4-ControlMethods.md)。

## 開始使用

### MuMu Android 操作

雙擊 `start.cmd` 開啟 MuMu 面板，按「連線」讀取局面。面板提供合法動作單步、Laya 單步、連續接手本局與停止。連續接手會等待對手回合，遇到未確認操作即停止；新對局需重新啟動接手。每次開啟都處於觀察模式。首次 Laya 載入可能較久，停止後會在模型返回時取消輸入。

「新增牌組／編輯打法」可保存遊戲內牌組名稱、標準或開放模式，以及起手換牌、牌組邏輯與 combo 思路。每副牌組分開保存在 `deck-profiles.json`，選定後會加入 Laya 的換牌、選牌與出牌輸入。牌組代碼目前僅保存，不會自動匯入遊戲。

「開始連續爬牌」從主選單或牌組畫面開始，先載入模型，再用本機 OCR 確認模式與牌組名稱、排隊、操作對局並處理結算。局數設為 0 會持續執行，按停止可取消後續輸入。遇到未確認操作或未支援動作會停止。已完成連續兩局標準龍戰、跨局重新排隊及局數上限停止，合計 36 個操作取得日誌確認；兩局皆落敗，尚未驗證勝率與長時間穩定性。結果與速度記錄分別在 `data/ranked-results.jsonl`、`data/ranked-decisions.jsonl`。

「校準目前畫面」會顯示裝置截圖，依序點選指定位置；這些點擊只用於儲存相對座標。起手牌、一般選牌、手牌與場位各自按數量保存。內建平板佈局位於 `android_layout.py`，個別校準保存在本機 `android-calibration.json`。

`android_device.py` 透過 ADB 的 Android 觸控事件操作裝置，使用截圖的實際方向與解析度換算相對座標。Windows 游標與模擬器視窗位置不參與座標計算。`android_reader.py` 直接讀取裝置內的 Power.log，另存 `android-state.json`，與 Windows 日誌分開。

先在 Android 爐石的 `/sdcard/Android/data/com.blizzard.wtcg.hearthstone/files/log.config` 啟用 `[Power]`、`LogLevel=1`、`FilePrinting=True`、`Verbose=True` 並重新啟動遊戲。ADB 路徑與裝置連線埠請依自己的 MuMu 實例指定。

```powershell
.\.venv\Scripts\python.exe android_hands.py --adb 'D:/MuMu Player 12/nx_main/adb.exe' --serial 127.0.0.1:16384
```

CLI 預設只列出合法動作。使用獨立的 `android-calibration.json`；加上 `--action 動作鍵` 預覽計畫，或用 `--decide` 由本機 Laya／規則選擇。加上 `--execute` 執行一次並等待日誌確認。`data/android-evidence` 保存前後局面與執行結果。

MuMu 練習局已有三張／四張起手換牌、手下出牌、英雄能力、攻擊英雄、攻擊手下與結束回合的成功樣本，也完成 Laya 決策後出牌。四張換牌曾在 MuMu 最小化、實體游標持續移動時成功，前景視窗前後相同；使用者也確認正常使用滑鼠時沒有受到干擾。另已在 MuMu 視窗縮為 1200×720 時成功攻擊手下，裝置截圖仍為 1920×1080；測試後恢復原視窗，前景視窗未變。修正畫面回合判定後，曾連續完成 22 個動作直到對局結束，並自動停止。這是接手進行中對局的驗證，尚不是從開局到結束的全程無介入測試。

發現及選牌會依完整候選清單提供單張或多張組合，並驗證遊戲實際提交的集合。`choice_overrides` 按候選數量保存位置；多選另需校準 `choice_confirm`。三選一發現已完成 Laya 選擇、觸控執行與日誌確認；特殊多選尚未實機驗證。

「倒轉／保留時間線」使用 `choice_card_overrides` 依選項卡牌識別定位，因為此介面排列與一般發現不同；倒轉選項已在天梯取得提交確認。倒轉後可能重用選牌編號，依事件順序辨別新選牌的修正已通過實際日誌回放，尚待新局實機覆蓋。

一般操作出手前會確認畫面上的回合按鈕已啟用，並等待手牌、場上卡牌與抽牌區動畫穩定，再重新核對局面。這能避免日誌先更新、畫面仍播放對手回合時拖牌。判定使用區域取樣與按鈕顏色，特殊介面或造型仍需實機驗證。出手前截圖與日誌一併保存在證據目錄。

決策使用 Power.log 的結構化局面與合法動作；Android 日誌增量讀取，模型常駐，畫面只用於動畫與介面確認。參考 [jev-brotato](https://github.com/banjtheman/jev-brotato) 的狀態→有限選項→操作流程，過期決策會在等待畫面及出手前重新取得。2026-09-27 連續兩局的 36 個已確認操作，決策中位數 0.234 秒；排除換牌的操作中位數 4.81 秒，包含動畫等待與日誌確認。這是該次實機樣本，不是整局速度保證。連續爬牌另依遊戲 TIMEOUT 預留 8 秒結束回合。

### Windows 輸入實驗

1. 執行 `powershell -File .\start.ps1 -Windows`，開啟原生 Windows 測試面板及讀取與 GPU 決策服務。每次開啟都是觀察模式。
2. 進入練習對局。起手選牌需分別校準先手三張、後手四張與確認按鈕；硬幣不列入可替換起手牌。
3. 按「校準座標」，把標記拖到對應英雄、英雄能力、結束回合、手牌及場上卡牌中心。Enter 儲存，Esc 取消。
4. 按「開啟輸入測試台」，選擇後端、測試條件與目前合法動作，再按「開始測試」。背景模式不需切回遊戲；SendInput 前景對照才需在 3 秒內切回爐石。
5. 看日誌結果，再另外標記目視結果與備註。F8 可隨時停止；背景模式目前只允許單步。

座標依目前客戶區高度縮放、水平置中，支援移動及縮放視窗，並保留不同手牌張數的校準。操作途中改變尺寸會停止；過窄視窗使目標超出客戶區時不會點擊。場上座標會依校準的間距推算，不同佈局仍需檢查。目前僅有少量單步成功樣本，尚不能估計整體成功率。

`stop.cmd` 會停止本專案的控制面板、讀取器及決策服務（包含虛擬環境啟動器的子程序）。關閉面板會停止操作，背景讀取與決策仍會運行。

## 支援範圍

- 讀取双方英雄、手牌、手下、地點、武器、秘密數量、法力和遊戲提供的動作／目標清單。
- Windows 讀取器每 100 毫秒讀取新增日誌；Android 由面板透過 ADB 讀取裝置日誌。
- 一般手下／法術／武器出牌、攻擊、英雄能力、地點與結束回合的操作計畫。
- 每步驗證局面指紋、合法選項及尺寸；出手後等待日誌確認，未確認時依下方重試規則處理。Android 操作不要求 MuMu 位於前景。
- 簡單、無觸發效果場面的攻擊斬殺搜尋，涵蓋嘲諷、聖盾、風怒與劇毒。未知效果、秘密與複雜觸發時不提供確定斬殺認證。
- 排除可見反傷造成的英雄自殺，以及未發現相關收益的滿血補血。
- 交換、可見死亡風險、費用組合、手牌／場位與資源保存的啟發式評分。這些評分不是完整對局模擬。
- 選定牌組時，Laya 比較全部已支援合法候選；未指定牌組時比較規則選出的至多六個候選。未填寫打法時，選項模糊或明顯低分會使用規則排序。

起手換牌會列出三張或四張起手牌的所有替換組合，確認使用遊戲 SendChoices 記錄的保留牌集合。Android 已加入指定目標戰吼的兩段操作，英雄目標已有實機確認。泰坦、同一實體的特殊替代操作等目前交由人處理。斬殺搜尋尚未包含任意法術連段、所有新卡互動與未知秘密。純卡牌文字不能完整反映所有附魔和動態效果。

Windows 只測試操作層可用 `powershell -File .\start.ps1 -Windows -HandsOnly` 啟動讀取器與面板。`.venv\Scripts\python.exe hands.py` 列出當前合法動作；加上 `--action 動作鍵` 預覽計畫，加上 `--execute` 才實際執行一次。Laya 起手選牌路徑已實作，尚未完成模型連接實機的驗證。

## 本機模型與資料

- Python 環境：`.venv`；Laya 0.3.20；PyTorch 2.11.0+cu128；RTX 4050。
- 模型放在 `.cache/huggingface`。運行時使用已下載快取，不將對局傳送給模型 API。
- `config.json` 記錄使用者確認的玩家名稱，每場重新對應 controller。
- `data/cards.zhTW.json` 為 HearthstoneJSON build 253216 的繁體中文卡牌資料。
- `state.json`：當前局面及讀取心跳。`observed_at` 是讀取器心跳，不代表每次都有新遊戲事件；`source_updated_at` 為日誌檔案更新時間。
- `advice.json`：建議、理由及方法。必須與目前局面指紋一致才能使用。
- `last-request.json`：最近的模型輸入。
- `execution.jsonl`：實際執行後的動作與確認結果。
- `sample-state.json`、`sample-advice.json`、`benchmark.json`、`replay-validation.json` 為歷史回放驗證，不能當成目前出牌指令。

模型分數未經爐石資料校準，不代表勝率。

## 手動輸入測試台

預設「即時畫面背景操作」使用 DWM 即時預覽顯示遊戲，同時以視窗對齊方式操作來源視窗。這仍會移動來源視窗，預覽並非獨立輸入管道。練習模式已有出牌、英雄能力、攻擊英雄、攻擊手下及結束回合的單步日誌確認；先手三張與後手四張選牌也有成功樣本。一次移動滑鼠期間的三張換牌漏選了一張；調整點擊保持時間後重測成功，但重測時游標靜止，尚不能證明問題已修好。

`data/input-evidence` 保存執行前後局面；輸入紀錄包含正規化計畫、像素計畫與操作期間游標／按鍵取樣。取樣只覆蓋程式檢查點，不能證明兩個檢查點之間的滑鼠狀態。

從主面板按「開啟輸入測試台」，或執行 `.venv\Scripts\python.exe app.py --test-ui`。開啟視窗不會操作遊戲。

可比較 Maa 普通 SendMessage、Maa PostMessage、簡易 PostMessage、AnchoredTouch、SendMessageWithWindowPos（視窗對齊）及 SendInput 前景對照。每次只執行你所選的合法動作；動作失效或換到另一場對局會取消，不改選其他卡牌。先在滑鼠靜止時測試，再比較移動滑鼠的條件。測試條件由你註記；程式記錄的是操作前後游標位置與前景狀態，不能證明中途完全沒有移動。

「已送出」僅表示輸入後端返回；「日誌已確認」表示觀察到預期局面變更。未確認不等於後端必然不支援。你可以選取紀錄查看座標，另填目視成功、無反應或點錯／不確定及備註。多人同時操作仍可能影響歸因。

`input-tests.jsonl` 保存執行結果，`test-observations.jsonl` 保存目視註記；兩者僅存在本機，不上傳 GitHub。測試台顯示最近 100 筆歷史以及本次新增紀錄。出牌及英雄能力測試會實際消耗資源，結束回合需手動選取再開始測試；指定目標戰吼尚未支援。「遊戲視窗復位」會最大化遊戲，執行中不可使用。

目前有日誌確認的樣本是視窗對齊模式的英雄能力、拖牌與英雄攻擊；PostMessage 與 AnchoredTouch 先前測試未獲確認，且過程曾有手動操作與座標干擾，不能由此判定兩者不可用。所有背景模式都不會自動回退至實體滑鼠。視窗對齊模式操作期間會完全透明、可穿透，還原位置後才恢復顯示；因此遊戲會暫時消失，並非全程可見的固定視窗。觸控模式在遮擋時可能閃爍。

跨螢幕時，先以未按下滑鼠的定位等待 DPI／客戶區尺寸穩定，再重算座標並執行；操作途中再次改變尺寸仍會停止。實測游標留在副螢幕、遊戲 DPI 從 96 變成 120 時，英雄攻擊已獲日誌確認。後續英雄能力測試也確認操作前後位置與客戶區尺寸一致。紀錄包含預定位 DPI、尺寸、最終位置及焦點，方便核對不同螢幕條件。

已知基礎費用為 0 的卡牌（例如幸運幣）即使日誌省略 COST，也會列入遊戲允許的動作；明確 COST 標籤優先。未知費用不會一律當作免費。練習模式已確認在 0 法力時成功打出幸運幣。

### 最小化實驗

選「視窗對齊 SendMessage」，勾選「最小化測試」，再選合法動作並開始。已最小化的遊戲也會自動走這個流程。Maa FramePool 將遊戲透明、可穿透地還原，輸入完成並確認日誌後再次最小化。這是透明還原的偽最小化，並非遊戲一直維持 Windows 最小化狀態。助手保持透明直到輸入後端完成清理、視窗位置及最小化狀態還原。

2026-09-27 練習模式實測：1920×1009 客戶區的最小化英雄能力，以及 1366×768 客戶區的最小化蜘蛛騎士拖牌，均獲日誌確認；兩次游標前後相同、遊戲前後不在前景，結束時恢復最小化。普通 SendMessage 的背景英雄能力樣本未獲確認。這些結果尚未涵蓋所有長寬比、DPI、多螢幕或完整連續對局。

測試紀錄另含擷取尺寸、客戶區座標及最小化前後狀態。關閉面板會先要求停止並等待輸入清理完成。

## 從 repository 安裝

使用 Python 3.12 建立 `.venv`，安裝 `requirements.txt`；CUDA 版本的 PyTorch 請依本機 GPU 選擇官方套件。將 `config.example.json` 複製成 `config.json`，填寫自己的 BattleTag。`reader.py --logs` 可指定 Hearthstone Logs 路徑，預設為 `D:\Battle.net\Hearthstone\Logs`。

## HSReplay 參考資料與牌組打法

## 決策大腦

一般決策先選具體動作或卡牌，再選合法目標。來源、費用、攻血與合法目標會出現在選項中；每次只執行遊戲提供的一個完整動作，再重新觀察。Laya 的選擇機率與既有場面評分共同排序：評分只是有限度的偏好，高信心模型選擇仍可勝過它。`stages` 同時保留模型答案、最終選擇與是否受到評分調整。

多語 Laya 使用實際 tokenizer 驗證 1,024 總輸入／256 問題預算。選項過多時分批比較；長描述移到上下文，送出前核對編碼器沒有截斷選項。按需壓縮卡牌欄位及策略／效果文字，並記錄壓縮程度。方案比較超出預算時退回具體動作選擇；一般局面仍超出預算時停止，避免漏掉數值或候選。對手輸入只含公開場面、手牌數、剩餘法力及已公開出過的牌與次數；未揭露秘密不加入牌名紀錄。

`card_simulator.py` 搜尋出牌與手下攻擊的混合序列，正式決策上限為深度 16、寬度 32、60 毫秒。支援已核對的有限效果，包括普通手下、護甲能力、巔風飛龍戰吼、預知滑龍手牌龍族減費及部分不在此階段觸發的被動效果。巔風飛龍同類沿用實際觀察費用；[官方同類規則](https://hearthstone.blizzard.com/en-gb/expansions-adventures/the-lost-city-of-ungoro)取決於上回合種族。未知效果停止該搜尋分支，仍可由 Laya 從真實合法清單選擇後實際觀察結果。

`turn_search.py` 補充攻擊序列；`turn_end.py` 結算支援的回合結束效果，包括列舉砲手隨機射擊、聖盾、護甲、死亡移除及重新選目標。只有全部隨機分支都致勝才提供確定斬殺；一般結果保留機率。已完成結算的方案標為 `own_turn_end`，其餘明確標示局部推演與邊界。這不包含對手抽牌及未知的下一回合行動。

`survival.py` 以可見手下計算對手下回合的攻擊路線，包含嘲諷、聖盾、護甲及攻擊次數刷新。超時或未知效果回傳未確認；此範圍不含對手手牌、武器攻擊與英雄技能。若空過確定會被這些攻擊擊殺，且存在完整結算後能避開該路線的方案，優先執行保命方案；其他情況將風險交給方案評分與模型。

確定斬殺優先由程式選第一步；其餘最多五個方案交給 Laya 比較，也可選其他合法動作。模擬器產生的後續動作不能直接送到執行器。排位的 `data/ranked-decisions.jsonl` 保存回合、版本序號、完整決策資料與輸入確認，供回放核對。

目前不是全卡牌規則引擎，也尚無跨回合搜尋或勝率保證。23 個龍戰歷史局面的本機模型回放全部成功，其中 16 個有結算到回合結束的方案；這只證明流程與速度，不能證明打法品質。新版實戰已揭露抽象種類選擇容易低信心空過，因而改為具體動作選擇及有限評分偏好；這項修正仍需持續實戰驗證。
